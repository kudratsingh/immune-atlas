# Architecture

## Overview

```
data/cell-count.csv
        │
        ▼
 load_data.py ──► immune_atlas.db.loader ──► cell_counts.db (SQLite)
                                                   │
                                                   ▼
                                    immune_atlas.db.queries (SQL → DataFrames)
                                                   │
                     ┌─────────────────────────────┼──────────────────────────┐
                     ▼                             ▼                          ▼
         analysis.frequencies (P2)      analysis.response (P3)      analysis.subsets (P4)
                     │                             │                          │
                     └───────────────► immune_atlas.export ◄──────────────────┘
                                                   │
                        ┌──────────────────────────┼─────────────────────────┐
                        ▼                          ▼                         ▼
                  outputs/*.csv|md          outputs/plots/*.png     dashboard/public/data/bundle.json
                                                                             │
                                                                             ▼
                                                                  dashboard/ (Next.js, static)
```

Three layers, each with one job:

1. **Data layer** (`immune_atlas/db/`): schema, validation, loading, and read
   queries. The only code that talks to SQLite.
2. **Analysis layer** (`immune_atlas/analysis/`): pure functions over pandas
   DataFrames. No I/O, no database handles, no file paths. This is what makes the
   analysis unit-testable with ten-row synthetic frames and reusable from a
   notebook, an API, or the pipeline.
3. **Delivery layer** (`immune_atlas/export.py`, `immune_atlas/pipeline.py`, and
   `dashboard/`): turns analysis results into files and screens. The pipeline is a
   linear list of stages with timing and row-count metrics; the dashboard reads a
   single versioned JSON bundle.

## Data layer

### Schema (ADR-0001)

```sql
CREATE TABLE projects (
    project_id   TEXT PRIMARY KEY
);

CREATE TABLE subjects (
    subject_id   TEXT PRIMARY KEY,
    project_id   TEXT NOT NULL REFERENCES projects(project_id),
    condition    TEXT NOT NULL,
    age          INTEGER NOT NULL CHECK (age >= 0),
    sex          TEXT NOT NULL CHECK (sex IN ('M', 'F')),
    treatment    TEXT NOT NULL,
    response     TEXT CHECK (response IN ('yes', 'no'))   -- NULL when not applicable
);

CREATE TABLE samples (
    sample_id                  TEXT PRIMARY KEY,
    subject_id                 TEXT NOT NULL REFERENCES subjects(subject_id),
    sample_type                TEXT NOT NULL,
    time_from_treatment_start  INTEGER NOT NULL CHECK (time_from_treatment_start >= 0),
    UNIQUE (subject_id, sample_type, time_from_treatment_start)
);

CREATE TABLE cell_populations (
    population_id  INTEGER PRIMARY KEY,
    name           TEXT NOT NULL UNIQUE,
    display_name   TEXT NOT NULL,
    sort_order     INTEGER NOT NULL
);

CREATE TABLE cell_counts (
    sample_id      TEXT NOT NULL REFERENCES samples(sample_id),
    population_id  INTEGER NOT NULL REFERENCES cell_populations(population_id),
    count          INTEGER NOT NULL CHECK (count >= 0),
    PRIMARY KEY (sample_id, population_id)
);

CREATE INDEX idx_subjects_project   ON subjects(project_id);
CREATE INDEX idx_subjects_cohort    ON subjects(condition, treatment, response);
CREATE INDEX idx_samples_subject    ON samples(subject_id);
CREATE INDEX idx_samples_type_time  ON samples(sample_type, time_from_treatment_start);
CREATE INDEX idx_counts_population  ON cell_counts(population_id);

CREATE VIEW v_sample_totals AS
SELECT sample_id, SUM(count) AS total_count
FROM cell_counts GROUP BY sample_id;

CREATE VIEW v_cell_frequencies AS
SELECT c.sample_id AS sample,
       t.total_count,
       p.name       AS population,
       c.count,
       100.0 * c.count / t.total_count AS percentage
FROM cell_counts c
JOIN cell_populations p USING (population_id)
JOIN v_sample_totals  t USING (sample_id);
```

Why this shape, briefly (full rationale in ADR-0001): the CSV is a denormalised
join of four entities. Splitting them removes repeated subject metadata, lets
constraints enforce the data contract, and — most importantly for the scaling
question — stores counts in long format so a new population is a new row in
`cell_populations`, not a schema migration. `v_cell_frequencies` is the Part 2
table computed in SQL; pandas reads it rather than recomputing it.

### Loading

`load_data.py` → `immune_atlas.db.loader.run(csv_path, db_path)`:

1. Read CSV with explicit dtypes.
2. Validate (`validate.py`). Errors are collected and raised together with row
   references, so a bad file fails once with a complete report.
3. Delete any existing database file, create schema from `schema.sql`.
4. Insert in dependency order inside one transaction: projects → subjects →
   samples → populations → counts (melted to long). `executemany` with sorted
   input keeps the file byte-stable across runs.
5. Log counts per table and total duration; record them in metrics.

### Queries

`queries.py` returns DataFrames and never leaks `sqlite3` objects:

- `cell_frequencies(conn)` — `SELECT * FROM v_cell_frequencies` ordered by
  sample, population sort order.
- `cohort_frequencies(conn, *, condition, treatment, sample_type)` — frequencies
  joined with subject metadata for a cohort. Used by Part 3.
- `baseline_samples(conn, *, condition, treatment, sample_type, time)` — Part 4.1.
- `baseline_breakdown(conn, ...)` — three SQL aggregations for Part 4.2: samples
  per project, distinct subjects per response, distinct subjects per sex.
- `form_answer(conn)` — the mean B-cell query, so the number in the README is
  produced by code.

## Analysis layer

### `frequencies.py` (Part 2)

`compute_frequencies(counts_long: DataFrame) -> DataFrame` — given rows of
`(sample, population, count)`, returns the five-column table. Validates that
percentages sum to 100 per sample. Also `to_wide(...)` for the dashboard.

### `response.py` (Part 3, ADR-0002)

`compare_response(freqs: DataFrame, *, unit: Literal["sample", "subject"]) ->
ResponseComparison`. For each population:

- n per group, median, IQR, mean, SD
- Mann–Whitney U (two-sided), p-value
- rank-biserial effect size `r = 1 - 2U / (n_yes · n_no)`, with sign convention
  documented (positive = responders higher)
- Welch t-test p-value as a secondary check
- Benjamini–Hochberg q across the five populations (`scipy.stats.false_discovery_control`)
- flags: `significant_raw` (p < 0.05), `significant_adjusted` (q < 0.05)

`unit="subject"` first averages a subject's percentages across time points.
`compare_response_by_time(freqs)` runs the per-sample comparison within each
time point. All three feed the report and the dashboard.

### `subsets.py` (Part 4)

Thin: shapes the query results into the summary structure and asserts the
sample/subject distinction. Kept as a module so the pipeline stage and its tests
have a home; the work is in SQL.

### `plots.py`

`response_boxplots(freqs, out_dir)` — one PNG per population and one combined
2×3 figure. Consistent colours with the dashboard palette, jittered points over
the boxes, n per group in the axis label, Agg backend, fixed DPI and size so
files are reproducible.

## Delivery layer

### Pipeline

`pipeline.py` defines an ordered list of stages, each a function taking a
`PipelineContext` (paths, connection, metrics):

```
load_database → cell_frequencies → response_comparison → response_plots
→ baseline_subset → form_answer → dashboard_bundle → write_run_report
```

Each stage is wrapped in `Timer`; failures stop the run with a non-zero exit and
a log line naming the stage. `python -m immune_atlas.pipeline --only <stage>`
exists for development but `make pipeline` always runs everything.

### Outputs

All data files under `outputs/` are deterministic: sorted rows,
`float_format="%.6f"` for percentages and `%.4g` for p-values in CSV,
`sort_keys=True, indent=2` for JSON, no timestamps except in `pipeline_run.json`
(excluded from the determinism check). Plots are rendered with fixed size, DPI,
seed, and metadata so they are byte-stable within an environment; across
environments PNG bytes depend on the matplotlib build, so CI checks them
structurally rather than by diff. The same applies to `cell_counts.db`, whose
header records the SQLite library version.

`dashboard/public/data/bundle.json` is the only input the dashboard has. Its
schema is `contracts/dashboard-bundle.schema.json`; the exporter validates the
bundle against it before writing, and the dashboard generates its TypeScript
types from it (`npm run gen:types` → `src/lib/bundle.types.ts`, committed).

### Dashboard

Next.js (App Router) with `output: "export"`, TypeScript, Tailwind CSS, Visx for
charts. No server component of our own: the static build is hosted on Vercel and
`make dashboard` serves the same app locally with `next dev` on `0.0.0.0:3000`.

```
dashboard/
├── src/app/                      # routes: /, /samples, /response, /baseline, /methods
├── src/components/               # charts/, tables/, filters/, layout/
├── src/lib/
│   ├── bundle.ts                 # load + validate bundle at startup
│   ├── bundle.types.ts           # generated from contracts/
│   ├── filters.ts                # client-side filter model (pure functions)
│   ├── stats-format.ts           # p-value / percentage / n formatting
│   └── palette.ts                # responder / non-responder colours, population colours
├── public/data/bundle.json       # written by the pipeline
├── tests/                        # vitest unit + component tests
└── e2e/                          # playwright smoke tests
```

Data flow inside the app: `bundle.ts` loads and validates once; a `useBundle()`
hook exposes it; pages derive their views with pure functions in `lib/` so that
the same functions are unit-tested without rendering.

## Observability

`observability.py` provides:

- `configure_logging(level, json_format)` — console handler; JSON lines when
  `IMMUNE_ATLAS_LOG_JSON=1`.
- `get_logger(name)`.
- `Timer(name, metrics)` context manager.
- `Metrics` — counters and gauges keyed by stage (rows in, rows out, seconds,
  warnings), serialised to `outputs/pipeline_run.json` and echoed into the bundle's
  `run` section so the dashboard's Methods page can show data provenance.

Every pipeline stage logs start, row counts, and duration at INFO. Validation
problems log at ERROR with row references. There is no long-running service to
scrape, so metrics are file-based by design; the `Metrics` interface is shaped so a
Prometheus or OpenTelemetry exporter could replace the JSON writer without touching
the stages.

## Configuration

`config.py` holds the constants everything else imports:

```python
POPULATIONS = ("b_cell", "cd8_t_cell", "cd4_t_cell", "nk_cell", "monocyte")
FREQUENCY_COLUMNS = ("sample", "total_count", "population", "count", "percentage")
RESPONSE_COHORT = CohortFilter(condition="melanoma", treatment="miraclib", sample_type="PBMC")
BASELINE_TIME = 0
ALPHA = 0.05
```

Paths default to the repository root (resolved from `__file__`) and can be
overridden by environment variables (`IMMUNE_ATLAS_CSV`, `IMMUNE_ATLAS_DB`,
`IMMUNE_ATLAS_OUTPUTS`) so tests can run in temporary directories.

## Error handling

- Validation failures: `DataContractError` with a list of `(row, column,
  problem)`; the loader raises once with all of them.
- Missing inputs: clear `FileNotFoundError` messages naming the expected path and
  the `make` target that produces it.
- Statistics on degenerate groups (fewer than 3 values): the population row is
  emitted with `null` statistics and a warning recorded in metrics, never a crash.

## Testing (ADR-0005)

- `tests/unit/`: schema constraints, validator, loader (small synthetic CSVs),
  frequencies, response statistics (synthetic data with a planted effect and a
  null case), subsets, export formatting, bundle schema validation.
- `tests/integration/`: `python load_data.py` via subprocess; full pipeline on the
  real CSV into a temp directory; reference numbers from DATA_NOTES; determinism
  (run twice, compare bytes).
- Dashboard: Vitest for `lib/` and components; Playwright smoke tests against the
  static build.
- CI: `python`, `dashboard`, `pipeline` (runs `make setup && make pipeline`, then
  starts `make dashboard` in the background and curls it), `e2e`.
