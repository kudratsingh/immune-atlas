# CLAUDE.md

Operating guide for coding agents working in this repository. It states where the
requirements live, what has already been decided, and how work gets from a branch
onto `main`. Humans should start with [README.md](README.md).

## What this project is

Immune Atlas is a take-home assignment: a Python data pipeline plus an interactive
dashboard that analyses immune cell population counts from a clinical trial dataset
(`data/cell-count.csv`). The pipeline loads the CSV into SQLite, computes per-sample
relative frequencies, compares responders with non-responders for one treatment
cohort, and answers a set of baseline-cohort questions. The dashboard presents those
results for a drug developer (Bob) and a sceptical colleague (Yah) who wants to see
the statistics behind every claim.

## Source of truth, in order

1. `docs/SPEC.md` — the assignment, transcribed verbatim, plus the acceptance
   checklist derived from it. If code and SPEC disagree, the code is wrong.
2. `docs/ARCHITECTURE.md` — the system design: schema, pipeline stages, the data
   bundle contract between pipeline and dashboard, repository layout.
3. `docs/adr/` — decisions already taken and why. Do not relitigate them inside a
   task. If a decision must change, write a new ADR and raise it before implementing.
4. `docs/PLAN.md` — workstreams, their ordering, ownership, and acceptance criteria.
   Each workstream section is the brief for whoever picks it up.
5. `docs/DASHBOARD_UX.md` — personas, information architecture, and the visual
   direction for the dashboard. Frontend work follows it.
6. `docs/DATA_NOTES.md` — what is actually in the dataset (shapes, cohort sizes,
   invariants the loader must enforce).

## Commands

| Command            | What it does                                                        |
| ------------------ | ------------------------------------------------------------------- |
| `make setup`       | Installs Python and Node dependencies.                              |
| `make pipeline`    | Runs the full pipeline: database → tables → statistics → plots → dashboard data bundle. |
| `make dashboard`   | Starts the dashboard dev server on port 3000 (runs the pipeline first if outputs are missing). |
| `make test`        | Python unit and integration tests with coverage; dashboard unit tests. |
| `make lint`        | Ruff, mypy, ESLint, and TypeScript checks.                          |
| `make check`       | `lint` + `test` — the same gate CI applies.                         |
| `make clean`       | Removes generated files (database, outputs, dashboard bundle).      |

`python load_data.py` on its own must always work: it creates `cell_counts.db` in the
repository root from `data/cell-count.csv` with no arguments.

## Engineering conventions

**Python**

- Python 3.11+, fully type-annotated public functions, `ruff` for lint and format,
  `mypy` on the package. Line length 100.
- Every module starts with a one- or two-sentence docstring saying what the file is
  for. Public functions get a short docstring. Comments explain *why*, not *what*,
  and are rare. No commented-out code, no TODOs without an issue reference.
- Analysis functions are pure: they take and return DataFrames. Database access lives
  in `immune_atlas/db/queries.py` only. Analysis artifacts are written by `export.py`;
  `Metrics.write` owns the pipeline run report.
- Log through `immune_atlas.observability.get_logger(__name__)`. No `print` outside
  the CLI entry points.
- Outputs are deterministic: stable row ordering, fixed float formatting, no
  timestamps inside generated tables. `make pipeline` on a clean tree must leave
  the data outputs and the dashboard bundle unchanged (CI diffs them; the
  database and PNGs are checked structurally because their bytes vary by
  library build).
- Cell population names, output column names, and cohort filters are constants in
  `immune_atlas/config.py`. Never retype the string `"cd8_t_cell"` in analysis code.

**Dashboard**

- TypeScript `strict`, ESLint, Prettier. No `any`.
- The bundle JSON is the only data source. Types are generated from
  `contracts/dashboard-bundle.schema.json`; do not hand-write them.
- Follow `docs/DASHBOARD_UX.md` for structure, copy, and visual direction. It lists
  the generic patterns to avoid.
- Every chart has a data-table alternative and keyboard-reachable controls.

**Tests**

- Every module has unit tests. `tests/integration/` runs the real pipeline on the
  real CSV and asserts on outputs, including the known cohort sizes in
  `docs/DATA_NOTES.md`.
- Coverage gate: 90% for `immune_atlas/`, 80% for the dashboard.
- Tests must not depend on network access or on files outside the repository.

## Git workflow

- `main` is protected. Nothing lands on `main` except through a pull request with
  green CI. Never push to `main` directly, never force-push a shared branch.
- Branch names: `feat/<area>-<short-description>`, `fix/...`, `docs/...`,
  `chore/...`, `test/...`. One workstream per branch.
- Commits follow Conventional Commits: `feat(analysis): compare responders by
  population`. Imperative mood, subject ≤ 72 characters, body only when the *why*
  is not obvious from the diff. No trailers, no co-author lines, no tool attribution
  in commit messages or PR descriptions.
- PRs use the template in `.github/pull_request_template.md`. Keep them reviewable
  (target < 500 changed lines; split otherwise). After opening a PR, enable
  auto-merge: `gh pr merge --auto --squash`. Squash merges only; the PR title
  becomes the commit subject on `main`, so write it as a Conventional Commit.
- Branch protection requires branches to be current with `main`. After another PR
  merges, run `gh pr update-branch <number>` (or rebase) so CI re-runs before
  auto-merge fires.
- Commit generated outputs in the same PR as the code that changed them.

## Working in parallel

The coordinating agent owns `docs/PLAN.md` and the ordering it defines. Workstreams
marked parallel in the plan run in separate git worktrees so their working trees
never collide:

```
scripts/new_worktree.sh feat/analysis-response     # creates ../immune-atlas-wt/analysis-response
```

Each delegated workstream gets a brief containing: the PLAN.md section it
implements, the files and directories it owns, the interfaces it must not change
(schema, config constants, bundle schema), the acceptance criteria, and the tests it
must add. The rules for a delegated agent:

- Stay inside the owned paths. If a change outside them is needed, stop and report
  it rather than making it.
- Interfaces defined in `docs/ARCHITECTURE.md` and `contracts/` are fixed for the
  duration of the workstream. Propose changes; do not apply them unilaterally.
- Run `make check` before opening the PR. Report what was tested and anything left
  undone in the PR description.
- Remove the worktree after the PR merges: `git worktree remove <path>` and delete
  the branch.

## Definition of done

A workstream is done when all of the following hold:

1. Every acceptance criterion in its PLAN.md section is met and demonstrated in the
   PR description.
2. Unit tests exist for new code; integration tests updated where behaviour changed.
3. `make check` is green locally and CI is green on the PR.
4. Documentation touched by the change is updated in the same PR: module docstrings,
   README sections, ADRs, `docs/PLAN.md` status.
5. Generated outputs are regenerated and committed if the change affects them.

## Known traps

- Part 2 output column is `sample`, not `sample_id`. Column names and order are
  fixed: `sample, total_count, population, count, percentage`.
- Part 3 uses PBMC samples only, melanoma condition only, miraclib treatment only.
  Response is a subject-level attribute; each subject contributes three samples
  (days 0, 7, 14), so per-sample tests overstate independence. The primary analysis
  and the per-subject sensitivity analysis are both required — see ADR-0002.
- `response` is null for healthy / untreated subjects. Never coerce it to `"no"`.
- Part 4 counts subjects for response and sex, but samples for project. At baseline
  they coincide (one sample per subject), which is exactly the kind of coincidence a
  test should not rely on.
- Codespaces is the grading environment: `make dashboard` binds to `0.0.0.0:3000`,
  requires no manual steps, and the dashboard must not call a second server.
- `load_data.py` must run with no arguments and no package installation beyond
  `make setup`. It is a script, not a module entry point.
